# 未来机械产品知识与协作体系设计

日期：2026-09-06  
状态：已完成方案讨论，待用户审阅后实施

## 1. 目标

建立一套可长期维护的产品知识与协作体系，使产品负责人、开发者、业务和生产人员能够快速理解宁波未来机械的完整产品，安全访问所需资料，并在每次功能变化后同步更新产品档案、代码仓库文档和项目交接状态。

体系必须解决以下问题：

- 新对话或新开发者能够在较短时间内恢复当前项目上下文。
- 产品介绍、跨系统架构、业务规则和路线图有统一入口。
- 源码、接口、数据库结构和部署事实与具体 Git 版本关联。
- Obsidian 通过坚果云共享，但不承载生产数据库或敏感客户资料。
- 协作者能够分析业务数据，同时不直接暴露生产数据库文件和凭据。
- 复杂架构图同时提供可编辑源文件和通用预览图片。
- 产品专属 Skill 只在用户显式调用时运行，完成任务后同步更新知识体系。

## 2. 已确认决策

- 采用“Obsidian 产品主档 + Git 技术主档 + 受控数据入口”的双轨主档方案。
- Obsidian 实际 Vault 根目录为 `D:\Obsidian\未来机械\未来机械`。
- Obsidian 使用坚果云共享，采用分角色授权；核心开发者可编辑，其他人员默认只读或仅预览。
- 一期继续使用 SQLite 作为接单平台业务数据库，通过定时任务生成脱敏分析快照。
- 达到迁移门槛后升级至 RDS MySQL，并通过阿里云 DMS 提供细粒度、可审计的协作查询。
- 产品 Skill 名称为 `$future-machinery-product`，禁止隐式触发。
- Skill 更新仓库后先展示差异和测试结果，获得用户确认后才创建 Git 提交。
- 复杂架构图以 `.drawio` 为唯一可编辑源文件，并导出同名 `.png`；小型流程可以使用 Mermaid。

## 3. 信息主档边界

### 3.1 Obsidian 产品主档

Obsidian 保存面向全团队的产品知识：

- 产品定位、目标客户、服务承诺和业务闭环。
- 企业网站、钣金服务小程序、接单平台、波波工单和企业微信的职责。
- 跨系统架构、数据流、状态流和部署关系。
- 产品路线图、需求优先级、验收口径、风险和决策记录。
- 发布说明、协作指南、数据口径和脱敏分析结果。

Obsidian 不保存源码细节副本，不保存生产数据库、客户原始附件或任何凭据。

### 3.2 Git 技术主档

每个代码仓库保存与该仓库实现直接相关的事实：

- 源码、测试和部署配置。
- API 契约、数据结构、环境变量名称和集成说明。
- 与代码同步的技术架构图源文件和预览图。
- 仓库级 `README.md`、`Handoff.md`、`CHANGELOG.md`。
- 变更对应的提交、分支和验证结果。

跨系统产品路线图只在 Obsidian 维护，仓库文档通过链接或版本标识引用，避免两份完整产品说明发生漂移。

### 3.3 数据主档

生产数据库是业务事实的唯一主档。坚果云和 Git 仅接收批准后的脱敏汇总，不接收数据库原文件或完整业务明细。

## 5. 仓库文档设计


波波工单仓库至少维护：

```text

  README.md
  api-contract.md
  status-mapping.md

```

文档重组采用渐进方式，先建立导航和新目录，再按功能变更迁移，避免一次性移动全部旧文档造成链接失效。

## 6. 图表管理

- `.drawio` 是复杂图的主源文件，必须可在 diagrams.net 或兼容工具中继续编辑。
- 每个 `.drawio` 同时导出同名 `.png`，供 Obsidian、代码托管平台和不安装插件的协作者查看。
- PNG 只作为预览，不单独修改；源图变化后重新导出。
- 简单时序、状态机和目录关系允许使用 Mermaid，内容直接保存在 Markdown 中。
- 架构发生实质变化时，Skill 必须检查受影响图表；临时浏览器图不算正式交付。
- Obsidian 保存跨系统图；具体仓库保存与实现相关的图。必要时使用同一源图的受控副本，并在图中标注版本日期和来源仓库提交。

## 7. 坚果云协作

实际 Vault 作为独立共享文件夹同步。建议权限如下：

| 角色 | 权限 |
|---|---|
| 产品负责人 | 拥有者和最终审批人 |
| 核心开发者 | 上传下载，可编辑指定产品与技术目录 |
| 业务、客服、生产 | 只可下载或仅预览；按需开放限定目录编辑 |
| 外部协作者 | 指定目录、仅预览、限期授权 |

协作约束：

- 不同时大范围移动或重命名目录。
- 重大结构调整先写决策记录，再由一人执行。
- 出现冲突副本时保留两份，人工比较后合并，不直接覆盖。
- 使用通用 Markdown、Draw.io 和少量统一插件，避免依赖个人插件。
- 离职、项目结束或角色变化时立即回收共享权限。

## 8. 数据访问设计

### 8.1 一期：SQLite + 脱敏分析快照

接单平台继续独占访问 ECS 本地 SQLite。每日备份进入私有 OSS，但数据库及其 `-wal`、`-shm` 文件不得进入坚果云。

新增只读分析导出任务：

1. 从批准的数据视图读取字段。
2. 删除或掩码手机号、联系人、客户图纸、附件地址、付款凭据、内部成本和内部备注。
3. 输出按日期标记的 CSV 或 Excel 汇总，以及数据口径说明。
4. 将适合团队查看的文件写入 Obsidian 分析目录，再由坚果云同步。
5. 记录生成时间、数据截止时间和代码版本，避免把快照当成实时数据。

第一批建议指标：新需求数、首次响应时间、超时率、报价数、报价转订单率、交付周期、订单状态分布、来源渠道和异常待办数。

需要技术排障的原始数据必须按个案导出、最小化字段、限期保存，不把数据库副本发给开发者。

### 8.2 二期：RDS MySQL + DMS

出现以下任一情况时启动迁移评估：

- 多实例或多进程需要并发写入。
- SQLite 锁等待、备份窗口或恢复时间无法满足业务要求。
- 需要多人实时查询、细粒度权限、审批和完整审计。
- 数据规模、报表复杂度或可用性要求明显提升。

迁移后每位协作者使用独立 RAM 身份，通过 DMS 获得限时、最小范围的查询权限。手机号等字段设置为敏感列；普通开发者默认没有导出或变更权限；所有权限申请和操作保留审计记录。

## 9. 产品 Skill 设计

Skill 安装位置：`C:\Users\luoch\.codex\skills\future-machinery-product`。

Skill 使用显式触发策略，核心职责：

1. 读取 Obsidian `首页.md` 与 `00-产品总览/当前状态.md`。
2. 读取项目根 `Handoff.md`，定位相关仓库。
3. 检查相关仓库工作区、分支、最近提交、README、Handoff 和任务相关文档。
4. 报告已完成、待验证、阻塞、风险和建议执行范围。
5. 仅完成用户本次明确授权的产品或开发任务。
6. 按风险执行测试、接口验证或文档检查。
7. 更新受影响的 Obsidian 子系统页面、当前状态、更新日志和图表。
8. 更新受影响仓库的技术文档、Handoff 和 CHANGELOG。
9. 展示文件差异、验证结果和待提交文件。
10. 取得用户确认后，才创建范围明确的 Git 提交；不自动推送。

Skill 必须遵守以下安全边界：

- 不记录或复制密码、私钥、AccessKey、AppSecret、Token、完整手机号和客户附件。
- 不把旧 Handoff 或 Obsidian 描述当成已验证线上事实，必须与代码和当前环境核对。
- 工作区存在他人未提交改动时不得覆盖或自动纳入提交。
- 不因“更新文档”自动获得部署、数据库变更、外部消息或云资源修改权限。
- 无法访问某个仓库或 Vault 时明确标记待验证，不虚构进度。

## 10. 新窗口快速接续

用户在新窗口输入：

```text
$future-machinery-product 请核对当前状态并继续下一阶段。
```

Skill 执行：

```text
读取产品当前状态
→ 读取根 Handoff
→ 检查相关 Git 仓库和最近提交
→ 核对测试与部署状态
→ 输出当前进度、风险和下一步
→ 经用户授权继续任务
→ 更新产品档案和仓库记录
→ 展示差异
→ 用户批准后提交
```

每次任务结束，`当前状态.md` 与相关 `Handoff.md` 必须指向同一阶段和下一步。更新日志保存历史，当前状态只保留最新事实。

## 12. 验收标准

- Obsidian 首页可在三次点击内到达任一子系统、路线图或当前状态。
- 新开发者只阅读首页、产品全景、当前状态和对应仓库 Handoff 即可了解工作边界。
- 每个复杂架构图同时存在可编辑 `.drawio` 和可查看 `.png`。
- Obsidian、Git 和数据主档的职责无冲突，不保存禁止内容。
- Skill 通过快速验证，且只能显式调用。
- 在新对话中调用 Skill 后，能够读取真实仓库状态并指出未完成任务。
- 任一产品更新完成后，Obsidian 当前状态、更新日志和相关仓库文档同步更新。
- 未经用户确认不创建 Git 提交，未经明确授权不推送、不部署、不修改生产数据。
